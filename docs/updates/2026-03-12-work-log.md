## 一、修復 #4：Entity 方法使用 inline 錯誤字串

### 問題
`entity/merchant.go`、`player.go`、`manager.go`、`tag.go`、`level.go`、`agent.go` 的 `IsValid()` 及業務方法直接 `return errors.New("字串")`，導致呼叫端無法用 `errors.Is()` 進行精確錯誤比對。

### 解決方案
在 `internal/domain/errmsg/errors.go` 新增 **18 個 sentinel error**，所有 entity 方法改為回傳這些常數：

| Entity | 新增 Sentinel Errors |
|--------|---------------------|
| Merchant | `ErrMerchantGlobalIDEmpty`、`ErrMerchantNameEmpty`、`ErrMerchantDisplayNameEmpty`、`ErrMerchantAPIKeyEmpty` |
| Player | `ErrPlayerGlobalIDEmpty`、`ErrPlayerAccountEmpty`、`ErrPlayerNoMerchant`、`ErrPlayerInvalidLevelID` |
| Manager | `ErrManagerGlobalIDEmpty`、`ErrManagerAccountEmpty`、`ErrManagerNoMerchant` |
| Tag | `ErrTagGlobalIDEmpty`、`ErrTagNameEmpty`、`ErrTagNoMerchant` |
| Level | `ErrLevelGlobalIDEmpty`、`ErrLevelNameEmpty`、`ErrLevelNoMerchant` |
| Agent | `ErrAgentGlobalIDEmpty`、`ErrAgentAccountEmpty`、`ErrAgentNoMerchant` |

各 entity 檔案移除 `"errors"` import，改 import `errmsg` 套件。

### 統計
- Commit：`89802fe`
- 修改檔案：7 個（`errmsg/errors.go` + 6 個 entity）

## 二、修復 #5：Handler 在有 Context 情境下使用非 Context 日誌方法

### 問題
`http_handler.go` 中所有 handler 都有 `c *gin.Context` 可取得 request context，卻使用 `ErrorLog()`/`InfoLog()`/`WarnLog()`（無 context 版本），導致日誌缺失 trace ID 關聯。`batch_processor.go` 中多個有 `ctx context.Context` 參數的函數也有相同問題。

### 解決方案
將所有在「有 context 可用」情境下的非 context log 呼叫，換成帶 context 版本：

**`http_handler.go`（14 處）：**
- 7 個 handler 中的 `ErrorLog` → `ErrorWithContext(c.Request.Context(), ...)`
- `SendKDSTestEvent` 中 3 個 `ErrorLog` + 1 個 `InfoLog` → 使用 `ctx`（已為 `c.Request.Context()`）
- `PlayerLogin` 中 `WarnLog` + `ErrorLog` + `InfoLog` → 使用 `c.Request.Context()`

**`batch_processor.go`（11 處）：**
- `Start`/`Stop`：`InfoLog` → `InfoWithContext(ctx, ...)`
- `handleSyncFallback`：2 個 `ErrorLog` + 1 個 `InfoLog` → 使用 `ctx`
- `processBatch`、`batchUpsertPlayers`、`batchPublishEvents`：共 7 個 `InfoLog`/`ErrorLog` → 使用 `ctx`

**保留不動：**`SetBlockOnFull`、`SetBatchConfig`、`SubmitPlayer` 中的 log（lifecycle/config 層級，無 request context）。

### 統計
- Commit：`5e1f898`
- 修改檔案：2 個

## 三、修復 #6：TracingService 被實例化兩次

### 問題
三個服務（web/consumer/worker）的 `initializeServices()` 各自呼叫 `tracing.NewTracingService(cfg)` 建立第一個 TracingService（用於 shutdown），但 Wire DI 函數（`InitializeWebServer` 等）內部的 `provideTracingService` 又獨立建立第二個。

結果：
- Handler/UseCase/Worker 使用的是第二個 TracingService 的 tracer
- cleanup 時 `s.tracer.Shutdown(ctx)` 關閉的是第一個（未被使用的那個）
- OTel span 正常結束，但 `FlushAndShutdown` 實際對另一個 provider 呼叫 → 可能導致 trace 遺失

### 解決方案
**將 TracingService 的所有權提升到 cmd 層，Wire 改為接收外部傳入的實例：**

`wire.go`：
- `baseSet` 移除 `provideTracingService`
- 4 個 injector 函數（`InitializeWebServer`、`InitializeWorkerServer`、`InitializeWorkerComponents`、`InitializeConsumerHandler`）加入 `tracingService infrastructure.TracingService` 參數

`wire_gen.go`（手動同步）：
- 4 個函數加入參數，移除 `provideTracingService(cfg)` 呼叫及其 error handling
- 更新 `baseSet` 宣告

3 個 cmd 檔案：
- `cmd/web/web.go`：傳入 `tracer` 至 `InitializeWebServer`
- `cmd/consumer/consumer.go`：傳入 `tracer` 至 `InitializeConsumerHandler`
- `cmd/worker/worker.go`：傳入 `tracer` 至 `InitializeWorkerComponents`

`test/redis_to_worker_test.go`：傳入 `mocks.NewNilTracingService()`

現在每個服務只有一個 TracingService 實例，cmd 層用它做 shutdown，同一個實例也流入所有 handler/usecase。

### 統計
- Commit：`64143aa`
- 修改檔案：6 個
