## 一、架構審計

### 背景
fat-identity-cat 是較早期的專案，已有一段時間沒有更新。以 fat-event-cat 和 fat-guardian-cat（較新的同系列專案）作為參考標準，進行全面的架構比較審計。

### 審計方法
透過 5 個平行 AI agent 分別從不同角度審計：
1. Infrastructure 層、Config、Logging 模式
2. Domain 層設計、Port/Interface、錯誤處理
3. 依賴注入（Wire）、Adapter 層結構
4. HTTP Handler、Use Case 實作模式
5. Observability（Tracing、Metrics）、測試結構

### 審計結果
共發現 20 個問題，分為四個嚴重等級：

**嚴重（P0）：3 個**
- Domain Port 介面直接暴露 Redis、OTel、asynq 框架型別（違反 Clean Architecture）
- `AsyncLogger` 的非 Context 方法全部為空實作，靜默丟棄日誌
- 缺少 OpenTelemetry Metrics 實作

**高（P1）：4 個**
- Entity 方法使用 inline 錯誤字串，無法 `errors.Is()` 判斷
- Handler 在有 Context 的情境下仍使用非 Context 日誌方法
- `TracingService` 被實例化兩次（DI 外部和 Wire 內部各一次）
- 沒有 Domain Value Object

**中（P2）：8 個**
- Entity 實作 JSON 序列化（應在 adapter 層處理）
- `LoggerFiled` typo 傳播至所有 logger 相關檔案
- Tracing 套件設計問題（dead statement、version 硬編碼、無 enabled guard）
- 巨型單一 HTTPHandler struct
- Config 缺少 mapstructure 標籤和環境判斷方法
- Dead code（`decryptAPIKey`、`parseCorsOrigins`、dead branch）
- 整合測試缺少 build tag
- Runtime type assertion in handler

**低（P3）：5 個**
- Adapter 缺少編譯時介面合規斷言
- `PlayerLevel` 型別重複定義
- Wire DI 圖不完整
- 依賴版本落後（Go 1.24 vs 1.25、OTel v1.37 vs v1.40 等）
- `fmt.Printf` 用於 cache 錯誤日誌

## 二、修復：Domain Port 層框架型別洩漏（P0 問題 #1）

### 問題描述
三個 Domain Port 介面直接引用具體的基礎設施框架型別：

| Port 檔案 | 洩漏型別 |
|-----------|---------|
| `domain/ports/outbound/infrastructure/cache.go` | `redis.Pipeliner`、`*redis.Client`、`*redsync.Mutex`、`*redsync.Redsync` |
| `domain/ports/outbound/infrastructure/tracing.go` | `trace.Span`、`attribute.KeyValue`、`codes.Code`、`trace.SpanStartOption` |
| `domain/ports/outbound/service/queue.go` | `asynq.Handler`（`WrapHandlerWithTracing`） |

### 解決方案（方案 B：務實分層修正）

**新增 Domain 型別：**
- `entity.Span` interface（`End`/`RecordError`/`AddEvent`/`SetStatus`）
- `entity.SpanAttr` + helper funcs（`StringAttr`/`IntAttr`/`Int64Attr`/`BoolAttr`）
- `entity.CacheSetEntry`
- `infrastructure.DistributedLockService` + `DistributedMutex` + `LockOptions`

**Port 介面變更：**
- `CacheManager`：移除 5 個 Redis 方法，新增 `BatchSet`/`BatchDelete`
- `TracingService`：所有方法改用 `entity.Span`/`entity.SpanAttr`/`ok bool`
- `QueueService`：移除 `WrapHandlerWithTracing`

**Infrastructure 新增：**
- `infrastructure/tracing/span.go`：`otelSpan` wrapper 實作 `entity.Span`，含 type-switch attribute 轉換
- `infrastructure/cache/redis/lock.go`：`RedisLockService` 實作 `DistributedLockService`
- Redis `Manager.BatchSet`/`BatchDelete` 方法

**受影響的呼叫端（全部更新）：**
- 6 個 Use Cases：`attribute.*` → `entity.*Attr`、`Pipeline()` → `BatchSet`/`BatchDelete`、`ExecuteWithLock` 改注入 `DistributedLockService`
- KDS Consumer：`GetMutex` → `lockService.GetLock`、`batchMarkEventsProcessed` 改用 `BatchSet`
- KDS Producer：span attr 型別更新
- Worker Handler：新增 `wrapWithTracing` 私有方法（含完整錯誤處理邏輯）
- Tracing Middleware：attr 型別更新
- DI Wire：新增 `provideDistributedLockService`、`wire.Bind` 綁定具體型別
- 所有 Mocks：`NilCacheManager`、`NilTracingService`、`TracingServiceMock`、`QueueServiceMock`

### Code Review 修正
Code Review 發現 `wrapWithTracing` 遺漏舊版的錯誤處理邏輯，已補回：
- `RecordSpanError` + `RecordSpanStatus(false, ...)` 記錄失敗
- 區分 retriable/non-retriable 錯誤
- `TraceEvent` 記錄成功/失敗事件
