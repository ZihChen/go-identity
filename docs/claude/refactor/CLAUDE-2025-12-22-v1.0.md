# 玩家標籤資料同步優化

## 完成狀態
✅ **已完成實作** (2025-12-22)

## 功能概述
批次插入更新標籤的地方做了太多無效的DB I/O開銷，使用快取機制以及資料比對只做必要的更新

## 技術實作

### 問題分析
1. 批次插入更新標籤時執行了過多無效的 DB I/O 操作
2. 位置：`internal/application/usecase/tag/tag_usecase.go:113`
3. 原有實作：直接執行 `u.tagRepo.BatchUpsert(ctx, tagsToInsert)` 不管標籤是否真的需要更新

### 解決方案
實作快取感知的批次更新機制，透過 Redis 快取預先檢查標籤是否需要更新，只對真正有變動的標籤執行資料庫操作。

### 核心優化功能

#### 1. UseCase 層快取邏輯
**位置**: `internal/application/usecase/tag/tag_usecase.go:427`

**功能特性**:
- 🔍 **快取預檢查**: 在 UseCase 層使用 Redis 快取檢查標籤是否存在及最後更新時間
- 🔄 **智能比較**: 比較 name、updated_at、deleted_at 等欄位判斷是否需要更新
- ⚡ **只更新必要的標籤**: 過濾掉不需要更新的標籤，大幅減少資料庫操作
- 🚀 **非同步快取更新**: 更新後自動更新快取，不影響主流程效能
- 🏗️ **Clean Architecture 合規**: 快取邏輯在業務邏輯層，Repository 專注於資料存取

#### 2. Clean Architecture 設計

**快取鍵格式**: `tag:global_id:{global_tag_id}`  
**快取過期時間**: 5分鐘

#### 5. Pipeline 批次更新實作
**位置**: `internal/application/usecase/tag/tag_usecase.go:521`

**Pipeline 批次快取更新**:
```go
// 1. 獲取 Pipeline 連線
pipeline, err := u.cache.Pipeline()
if err != nil {
    u.updateTagCacheFallback(ctx, tags) // 回退機制
    return
}

// 2. 批次準備 SET 命令
cacheCommands := 0
for _, tag := range tags {
    cacheKey := fmt.Sprintf(consts.RedisTagGlobalIDKey, tag.GetGlobalTagID())
    tagData, err := json.Marshal(tag)
    if err != nil {
        continue // 跳過序列化失敗的標籤
    }
    
    // 添加 SET 命令到 Pipeline（快取 5 分鐘）
    pipeline.Set(ctx, cacheKey, string(tagData), 5*time.Minute)
    cacheCommands++
}

// 3. 執行 Pipeline
if cacheCommands > 0 {
    _, err = pipeline.Exec(ctx)
    if err != nil {
        u.updateTagCacheFallback(ctx, tags) // Pipeline 失敗回退
    }
}
```

**效能優勢**:
- ⚡ **網路優化**: N 次個別操作減少為 1 次 Pipeline 執行
- 🔄 **原子性**: 所有快取更新作為一個批次執行
- 🛡️ **雙重保障**: Pipeline 失敗時自動回退到逐個更新
- 📊 **性能監控**: 記錄批次大小和執行狀態

### 使用方式
**位置**: `internal/application/usecase/tag/tag_usecase.go:111`
```go
// 原有方式（直接批次更新所有標籤）
if err = u.tagRepo.BatchUpsert(ctx, tagsToInsert); err != nil {
    return fmt.Errorf("batch upsert tags failed: %w", err)
}

// 優化後方式（UseCase層快取感知邏輯）
// 1. 使用快取篩選需要更新的標籤
tagsToUpsert, err := u.filterTagsNeedingUpdate(ctx, tagsToInsert)
if err != nil {
    return fmt.Errorf("filter tags needing update failed: %w", err)
}

// 2. 只對需要更新的標籤執行資料庫操作
if len(tagsToUpsert) > 0 {
    if err = u.tagRepo.BatchUpsert(ctx, tagsToUpsert); err != nil {
        return fmt.Errorf("batch upsert tags failed: %w", err)
    }
    // 3. 非同步更新快取
    go u.updateTagCache(context.Background(), tagsToUpsert)
}
```

### 效能預期改善

#### 資料庫負載減少
- **預期減少**: 60-80% 的不必要 INSERT/UPDATE 操作
- **目標**: 將 39.38% 的 runtime 降至 10-15%
- **查詢次數**: 從 256,208 次大幅降低至實際需要更新的數量

#### 回退機制
- **快取不可用時**: 自動回退至原始 `BatchUpsert()` 方法
- **快取錯誤處理**: 快取讀取失敗時假設需要更新，確保資料一致性
- **零風險**: 不會因快取問題造成資料遺失

#### 快取策略
- **寫入策略**: Write-Through (更新資料庫後同步更新快取)
- **批次優化**: 使用 Redis Pipeline 進行批次 SET/DEL 操作，減少網路往返
- **即時清除**: 單一標籤更新後立即清除對應快取確保一致性
- **失效策略**: 提供 `InvalidateTagCache()` 方法手動清除快取
- **容錯設計**: 快取操作失敗不影響核心業務流程
- **回退機制**: Pipeline 失敗時自動回退到逐個操作，確保可靠性

#### Pipeline 實作特點
- **🔗 連線管理**: `u.cache.Pipeline()` 獲取 Pipeline 連線
- **📦 批次處理**: 單次 `pipeline.Exec()` 執行多個 SET/DEL 命令
- **⚡ 性能提升**: 網路往返從 N 次減少至 1 次
- **🛡️ 容錯機制**: Pipeline 建立或執行失敗自動回退
- **📊 詳細日誌**: 記錄批次大小、執行狀態和錯誤詳情

### 架構優勢
1. **Clean Architecture 合規**: 快取邏輯在 UseCase 層，Repository 層專注於資料存取
2. **正確的關注點分離**: 
   - Repository: 純資料存取，無業務邏輯
   - UseCase: 業務邏輯 + 快取策略
   - Infrastructure: 快取實作細節
3. **向後相容**: 保留原有 `BatchUpsert()` 方法，不影響現有功能
4. **測試友善**: UseCase 可注入 Mock CacheManager 進行單元測試
5. **維護性**: 快取邏輯集中在業務層，易於理解和維護
6. **擴展性**: 快取模式可應用到其他 UseCase，無需修改 Repository
